# Software Development Workflow: Claude, Hermes, Ollama, and GitHub

## Architecture

- **Claude Free:** Product owner and architect. Turns goals into small stories with clear acceptance criteria.
- **Hermes:** Coordinator and Kanban manager. Dispatches implementation and review tasks in series.
- **Ollama:** Runs local implementation and review agents.
- **OpenCode:** Coding tool used by agents on the dedicated Hermes VM.
- **GitHub:** Hosts repositories, pull requests, reviews, and merges.

The intended workflow is:

```text
Claude writes small stories
        ↓
Hermes creates and manages Kanban tasks
        ↓
Ollama/OpenCode implements one story and opens a PR
        ↓
A separate Ollama/OpenCode agent reviews the PR
        ↓
If approved, the reviewer merges it
        ↓
Hermes moves on to the next ready story
```

Use Claude interactively through the Claude application for planning. Do not assume Claude Free provides a continuously callable API; the Claude application and Anthropic API are separate products.

## 1. Prepare the Hermes VM

Log in as the `opencode` user and verify the installed tools:

```bash
ssh opencode@<hermes-vm-ip>

hermes --version
opencode --version
git --version
gh --version
```

Verify GitHub SSH access and GitHub CLI authentication as the same user Hermes will use:

```bash
ssh -T git@github.com
gh auth status
```

SSH access allows Git operations over SSH. It does not necessarily authenticate GitHub CLI API operations, so confirm `gh auth status` succeeds before automating PR creation and merging.

Create a workspace:

```bash
mkdir -p ~/workspace
mkdir -p ~/logs
```

Clone a test repository:

```bash
cd ~/workspace
git clone git@github.com:<owner>/<repository>.git
cd <repository>
git remote -v
```

The Hermes installation command used on this VM is:

```bash
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
```

## 2. Verify Ollama connectivity

Set the remote Ollama server address:

```bash
export OLLAMA_HOST=http://<ollama-vm-ip>:11434
```

Check that the server responds and that the model is installed:

```bash
curl "$OLLAMA_HOST/api/tags"
```

Test a generation request:

```bash
curl "$OLLAMA_HOST/api/generate" \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "qwen3-coder:30b-a3b",
    "prompt": "Reply with exactly: ollama-ok",
    "stream": false
  }'
```

If the request fails, check that Ollama is listening beyond `127.0.0.1`, that TCP port `11434` is allowed through the VM firewall, and that VM-to-VM network traffic is permitted.

Start with the coding model recommended in your homelab customization guide. If memory use or latency is too high, consider using a smaller model for review and routine tasks.

## 3. Configure Hermes profiles

Back up Hermes configuration before changing it:

```bash
tar czf ~/.hermes-backup-$(date +%Y%m%d-%H%M%S).tar.gz ~/.hermes
```

Inspect the configuration generated by your installed version:

```bash
sed -n '1,240p' ~/.hermes/config.yaml
```

Use separate profiles for separate responsibilities:

- `orchestrator`: manages the board and dispatches tasks.
- `implementer`: implements one assigned story using Ollama.
- `reviewer`: reviews one linked PR using Ollama.
- Optional: `test-fixer` or `release-manager`.

The conceptual configuration is:

```yaml
profiles:
  orchestrator:
    model: <hermes-orchestration-model>
    tools:
      - kanban

  implementer:
    model: qwen3-coder:30b-a3b
    provider: ollama
    base_url: http://<ollama-vm-ip>:11434/v1
    api_key: ollama

  reviewer:
    model: qwen3-coder:30b-a3b
    provider: ollama
    base_url: http://<ollama-vm-ip>:11434/v1
    api_key: ollama
```

Treat this as a configuration pattern, not guaranteed copy-and-paste syntax. Check the provider and profile format supported by the installed Hermes version.

Hermes configuration is stored under `~/.hermes/`. Inspect its built-in help before using commands:

```bash
hermes --help
hermes kanban --help
```

## 4. Define agent responsibilities

### Orchestrator

The orchestrator should:

- Dispatch only ready tasks.
- Assign one implementation story at a time.
- Never edit application code.
- Never approve its own implementation work.
- Never merge unless a separate review task approved the PR.
- Record failures and blockers on the board.
- Apply a bounded retry policy.

### Implementer

The implementer should:

- Work on exactly one assigned story.
- Read repository instructions before changing code.
- Create a task-specific branch.
- Make only the changes needed for the story.
- Add or update tests.
- Run the relevant checks.
- Push the branch and open a PR.
- Record the PR URL and test results on the task.

### Reviewer

The reviewer should:

- Review only the PR linked to its task.
- Check the diff against the story and acceptance criteria.
- Run tests independently.
- Check for security, compatibility, and regression risks.
- Request changes when needed.
- Approve and merge only the referenced PR.
- Record the result on the board.

## 5. Add repository instructions

Add an `AGENTS.md` file to each repository. For example:

```markdown
# Agent Development Instructions

## Workflow

Every implementation task must:

1. Use a task-specific branch.
2. Make the smallest change that satisfies the story.
3. Add or update automated tests.
4. Run formatting, linting, type checks, and relevant tests.
5. Open a pull request.
6. Include verification results in the pull request description.

## Prohibited actions

- Do not push directly to `main`.
- Do not merge your own pull request.
- Do not rewrite unrelated code.
- Do not modify secrets or production configuration.
- Do not delete tests to make them pass.
- Do not change dependency versions unless the story requires it.

## Pull request requirements

The PR description must include:

- Summary
- Story ID
- Acceptance criteria
- Files changed
- Tests run
- Known limitations
- Migration or deployment notes
```

Configure GitHub branch protection on `main`:

- Require pull requests.
- Require CI checks.
- Block force pushes.
- Prevent direct pushes where possible.
- Require human approval for high-risk repositories or changes.

## 6. Have Claude create small stories

Use Claude as the product owner and architect. Give it project context such as the product goal, architecture, technology stack, existing behavior, and relevant repository instructions.

Suggested Claude project instructions:

```text
You are the product owner and software architect for this repository.

Turn product goals into small implementation stories for an autonomous local coding workflow.

Each story must:
- Be implementable in one focused coding session.
- Change one coherent behavior.
- Have explicit acceptance criteria.
- Identify likely files or subsystems.
- Include tests.
- State dependencies.
- Avoid combining unrelated frontend, backend, database, and deployment work.
- Prefer vertical slices over technical-layer tasks.

Do not write implementation code unless requested.
Do not create stories that depend on undocumented assumptions.
```

Ask Claude for stories in a consistent format:

```markdown
## Story: Add password reset request endpoint

### Goal

Allow a user to request a password reset email.

### Acceptance criteria

- `POST /auth/password-reset/request` accepts a valid email address.
- The endpoint returns the same response for existing and unknown addresses.
- A reset token is stored hashed, with a 30-minute expiry.
- A reset email job is queued for known users.
- Rate limiting is applied per IP and email address.
- Unit and integration tests cover success, unknown email, expired token, and rate limiting.

### Scope

- Authentication API
- Reset-token persistence
- Email-job enqueueing
- Tests

### Out of scope

- Frontend reset form
- Email template redesign
- Password reset completion endpoint

### Dependencies

- Existing email queue
- Existing user model

### Suggested branch

`story/password-reset-request`
```

Have Claude produce one story or a small ordered batch at a time. Review the stories before putting them on the board.

## 7. Create implementation and review tasks

Initialize the Kanban board:

```bash
hermes kanban init
```

Check the commands available in your installed version:

```bash
hermes kanban --help
hermes kanban create --help
hermes kanban link --help
```

Create the implementation task:

```bash
hermes kanban create \
  "Implement story: password reset request endpoint" \
  --assignee implementer
```

Create a separate review task:

```bash
hermes kanban create \
  "Review and merge PR for password reset request endpoint" \
  --assignee reviewer
```

Link the review task to the implementation task using the returned task IDs:

```bash
hermes kanban link <review-task-id> <implementation-task-id>
```

Add the story, repository, and acceptance criteria to the implementation task. For example:

```bash
hermes kanban comment <implementation-task-id> "$(cat <<'EOF'
Repository: <owner>/<repository>
Base branch: main
Workspace: ~/workspace/<repository>

Acceptance criteria:
- POST /auth/password-reset/request accepts a valid email.
- Existing and unknown addresses receive equivalent responses.
- Reset tokens are stored hashed and expire after 30 minutes.
- A reset email job is queued for known users.
- Rate limiting is applied.
- Tests cover success, unknown user, expiry, and rate limiting.

Required output:
- Task-specific branch
- GitHub PR
- Tests and checks executed
- Changed files
- Known residual risks

The task is not complete until a GitHub PR exists and its URL is recorded here.
EOF
)"
```

## 8. Dispatch one story at a time

Start with a dry run:

```bash
hermes kanban dispatch --dry-run
```

Inspect the tasks:

```bash
hermes kanban list
hermes kanban show <implementation-task-id>
```

Dispatch the ready implementation task:

```bash
hermes kanban dispatch
```

Monitor it:

```bash
hermes kanban list
hermes kanban show <implementation-task-id>
hermes kanban tail <implementation-task-id>
```

Once implementation is complete, the linked review task should become ready. Dispatch again:

```bash
hermes kanban dispatch
```

Keep implementation serial initially. This reduces GPU contention, avoids racing dependent stories, and makes failures easier to diagnose.

## 9. Implementer workflow

The implementation agent should inspect the repository, create a branch, make the change, run checks, and open a PR:

```bash
cd ~/workspace/<repository>

git fetch origin
git checkout main
git pull --ff-only origin main

git checkout -b story/password-reset-request
git status --short
```

Before editing, read project instructions such as `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, and `README.md`.

Run the repository's actual checks. Example commands:

```bash
make test
make lint
make typecheck
```

Commit and push:

```bash
git add <specific-files>
git commit -m "feat(auth): add password reset request endpoint"
git push -u origin story/password-reset-request
```

Open the PR:

```bash
gh pr create \
  --base main \
  --head story/password-reset-request \
  --title "feat(auth): add password reset request endpoint" \
  --body-file /tmp/pr-body.md
```

The PR description should include:

```markdown
## Summary

Implements password reset request handling.

## Story

Hermes task: <implementation-task-id>

## Acceptance criteria

- [x] Valid email accepted
- [x] Existing and unknown users receive equivalent responses
- [x] Tokens stored hashed
- [x] Tokens expire after 30 minutes
- [x] Email job queued
- [x] Rate limiting applied

## Verification

- `make test`
- `make lint`
- `make typecheck`

## Residual risk

- Email provider integration was tested with the local queue only.
```

Record the PR URL and checks on the implementation task:

```bash
hermes kanban comment <implementation-task-id> \
  "PR opened: https://github.com/<owner>/<repository>/pull/<number>
   Tests: make test, make lint, make typecheck
   Branch: story/password-reset-request"
```

## 10. Review and merge workflow

The reviewer should inspect the PR independently:

```bash
gh pr view <number> --repo <owner>/<repository>
gh pr diff <number> --repo <owner>/<repository>
gh pr checks <number> --repo <owner>/<repository>
```

If local inspection is useful:

```bash
cd ~/workspace/<repository>
gh pr checkout <number>
```

### If changes are needed

Request changes, describe the problem, and leave the PR open:

```bash
gh pr review <number> \
  --repo <owner>/<repository> \
  --request-changes \
  --body "The endpoint leaks whether an email exists. Return an equivalent response for both cases and add the required regression test."
```

Add a Kanban comment describing the issue. Create or requeue a fix task, and review the new commit before approving.

### If approved

Approve the exact PR:

```bash
gh pr review <number> \
  --repo <owner>/<repository> \
  --approve \
  --body "Acceptance criteria verified; tests pass."
```

Then merge it:

```bash
gh pr merge <number> \
  --repo <owner>/<repository> \
  --squash \
  --delete-branch
```

Record the approval, merge, and checks on the review task. Do not mark it complete if checks are failing or pending, changes have been requested, or the PR contains unrelated changes.

## 11. Add failure handling

### Implementation failure

- Record the error and attempted commands on the task.
- Mark it blocked or retryable.
- Retry only a limited number of times.
- If the agent remains stuck, ask Claude or a human to split or revise the story.

### Review failure

- Keep the PR open.
- Request changes.
- Create or link a fix task.
- Do not approve or merge until the new changes have been reviewed.

### Stale worker

Before restarting a stale task, check whether the agent already pushed a branch or opened a PR:

```bash
hermes kanban show <task-id>
gh pr list --repo <owner>/<repository> --search "<task-id>"
git branch -r
```

## 12. Set a human-approval boundary

Consider requiring human approval for changes involving:

- Authentication or authorization
- Database migrations
- Payment code
- Secrets and credentials
- Deployment or infrastructure
- Destructive data operations
- Production configuration
- Changes to CI or branch protection

The reviewer instructions can include:

```text
Never merge automatically if the PR changes:
- migrations/
- auth/
- permissions/
- deployment/
- infrastructure/
- secrets
- payment/
- production configuration

Instead, request human review and leave the PR open.
```

## 13. Automate dispatching after the workflow is tested

First test dispatching interactively:

```bash
while true; do
  hermes kanban dispatch
  sleep 60
done
```

After confirming it works reliably, run it under a supervisor such as systemd. Find the Hermes executable path:

```bash
command -v hermes
```

Example systemd unit:

```ini
[Unit]
Description=Hermes Kanban dispatcher
After=network-online.target

[Service]
Type=simple
User=opencode
WorkingDirectory=/home/opencode
ExecStart=/bin/sh -c 'while true; do /home/opencode/.local/bin/hermes kanban dispatch; sleep 60; done'
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

Adjust the executable path to match your VM, then enable the service:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now hermes-dispatcher
sudo journalctl -u hermes-dispatcher -f
```

Keep the dispatcher separate from the interactive Hermes gateway so that restarting one does not interrupt the other.

## 14. Run a harmless end-to-end test first

Choose a low-risk task, such as a small documentation update or a simple health-check endpoint.

1. Ask Claude for one small story.
2. Create an implementation task and a linked review task.
3. Run `hermes kanban dispatch --dry-run`.
4. Dispatch the implementation task.
5. Confirm the agent uses the right repository and Ollama model.
6. Confirm it creates a branch, pushes over SSH, and opens a PR.
7. Confirm the reviewer inspects the linked PR and runs checks.
8. Confirm the reviewer approves and merges it.
9. Confirm Hermes records the PR, checks, and merge result.

Do not begin with an authentication feature, database migration, or large refactor. Validate the control loop first.

## Recommended operating cycle

```text
Claude:
  product goal
      ↓
Claude:
  small story and acceptance criteria
      ↓
Hermes:
  create implementation task
  create linked review task
      ↓
Ollama/OpenCode implementer:
  branch → code → tests → PR
      ↓
Ollama/OpenCode reviewer:
  inspect → test → approve or request changes
      ↓
If approved:
  merge the exact PR
      ↓
Hermes:
  record result and start the next ready story
```
